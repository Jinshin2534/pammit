# パミットのAI：最新状況と開発方針

更新日：2026-10-02。本選予定日：2026-10-10。

AI担当・アプリ担当・ハード担当が、現在動く部分と今後の接続を確認するための入口。過去のAI計画書にある「葉も検出する」「中央の1個を選ぶ」などと食い違う場合、現在の開発範囲はこのページを優先する。完成した製品仕様を示す資料ではない。

## 現在の構成

```text
帽子カメラ / Raspberry Pi
  └─ 単一JPEG取得 ── Android / Pixel 7a
                         ├─ 果実検出：実機動作確認済み
                         ├─ 実ごとの明暗・葉のかぶり：試作評価中
                         ├─ 作業判断と位置付き音声：未完成
                         └─ 記録API / AWS：AI経路との統合は未完了
```

AI推論はスマートフォンで行う。AWSのクレジットは学習に利用可能だが、現時点の明暗・かぶりの探索実験はMacで実行した。Piの既存`GET /capture`からJPEGを取得するコードはAndroid検証アプリにある。実機でのPi→スマホ疎通、音声トリガー、最初の音声までの全経路は未検証。

| 項目 | 現在の状態 |
| --- | --- |
| 果実検出 | 既存ONNXをMacとPixel 7aで実行済み |
| Android | 果実検出のJava検証アプリがローカルにある。本体アプリへの統合は未完了 |
| 実の明暗 | 輝度基準、画像特徴、事前学習モデルの特徴を比較した |
| 葉のかぶり | 実単位の観察ラベルを作成し、分類器を探索評価した |
| 葉の個体検出・葉枠ラベル | 現在の必須範囲から外した |
| 摘む / 残す | 栽培判断としてのモデル・基準は未完成 |
| 位置付き音声案内 | 方針は確認済み。検証アプリへの実装・接続は未完了 |
| `unknown` | 必要な動作として合意。判定器の閾値と受け入れ基準は未確定 |

## 果実検出モデル

現在のモデルは一般的なYOLOの検出リストではなく、`heatmap`・`wh`・`offset`の3テンソルを出力する。前処理はRGB、1536×1536への縦横比を保ったレターボックス、ImageNet正規化。後処理で中心と枠を復元し、重複を除く。

元のモデルは内部にFP16演算を持ち、MacとPixelへ同一入力テンソルを渡しても出力が異なった。Androidには内部をFP32に変換した派生モデルを使う。同じFP32入力テンソルではP01の6候補について枠とスコアの再現性を確認した。JPEGの縮小処理はMac、Python、Androidで異なるため、元JPEGからの全経路が同一になる保証はない。

| モデル | SHA-256 |
| --- | --- |
| 元のFP16内部演算版 | `efa88e10315145bf1a39f958b22897d042ec5110c4166551286a4f752582b32f` |
| Android用FP32版 | `67fa5766fb5687158616075f825d678d37a21e160a2e19d50c4d72b4039c3dfd` |

モデル本体・ZIP・APK・元画像はGitへ含めない。端末間の再現性確認は、果実検出の正解率を測ったものではない。ユーザーの方針で、既存果実検出器の追加精度試験はいったん止めている。

### Pixel 7aの時間測定

2026-09-29、同梱P01画像、モデル読み込み後の同じ画面で5回実行した結果。

| 実行方式 | 前処理の中央値 | ONNX推論の中央値 | 枠復元の中央値 | 3工程の合計範囲 |
| --- | ---: | ---: | ---: | ---: |
| CPU | 333 ms | 521 ms | 3 ms | 844〜872 ms |
| XNNPACK | 331 ms | 478 ms | 3 ms | 806〜826 ms |

約0.8秒は**前処理・推論・枠復元の合計**。帽子からの画像転送、JPEG復号、トリガー、明暗・かぶり判定、音声開始は含まない。初回のXNNPACK実行は約1.78秒だった。NNAPIはONNX推論だけで約3.3秒となり、現時点の候補はXNNPACK。「トリガーから最初の音声まで1秒以内」はまだ実証していない。

## 何をラベル付けしたか

撮影済みのデータは主に収穫作業の動画。撮影当時の摘果・摘葉判断の正解がそろっているデータではない。そのため、現在は実の枠と、画像から見える状態を別々に記録する。

| 項目 | 値 | 意味 |
| --- | --- | --- |
| 果実の位置 | ピクセル座標の枠 | 画像内の実の位置 |
| `light_state` | `sunlit` / `shadowed` / `unclear` | 画像上の表面の明暗 |
| `leaf_cover_state` | `covered` / `not_covered` / `unclear` | 葉が実にかぶって見えるか |

`unclear`は明示的な判定不能ラベル。空欄とは区別する。画像上の明暗・かぶりだけから、日照時間、葉との物理接触、摘果すべきかを確定しない。「明るい」を一部の受光とするか、見えている表面の大半とするかはユーザーに確認中。

| セット | 使用場面数 | 果実の枠 | 明暗の二値ラベル | かぶりの二値ラベル |
| --- | ---: | ---: | ---: | ---: |
| 初回 P01〜P05 | 5（P03は0個で確認済み） | 54 | 48 | 47 |
| 追加 | 8（指定された1場面を除外） | 89 | 86 | 83 |
| 合計 | 13 | 143 | 134 | 130 |

初回P04の2個は状態ラベルが未入力で、ユーザー指定により状態判定の対象外。追加セットに入力された`take`5件は保全しているが、明暗・かぶりの教師ラベルや摘果の正解としては使っていない。

元動画ID、時刻、画像SHA-256と対象IDを保存している。園地ID・木IDは現データにない。同一動画のフレームを学習側と評価側へ分けず、ラベルのある10動画を単位に探索評価した。同じ日・園地の条件を含むため、未知の園地での性能とは扱わない。

## 最新の探索評価

`unclear`と未入力は二値分類の評価から外す。以下は全件を二値に判定した比較で、モデルが自動的に`unknown`へ保留した評価ではない。

| 方法 | 明暗の一致 / 134 | 陰の見逃し / 39 | かぶりの一致 / 130 | かぶりの見逃し / 30 |
| --- | ---: | ---: | ---: | ---: |
| 常に多数派を選ぶ | 95 | 39 | 100 | 30 |
| 輝度基準（10月2日修正後） | 97 | 10 | — | — |
| 色・明暗・縁の固定特徴＋分類器 | 97 | 13 | 99 | 10 |
| MobileNetV3 Smallの固定特徴＋分類器 | 102 | 17 | 81 | 22 |

一致数だけでは判断しない。例えばMobileNetの明暗102件一致でも、陰39件のうち17件を見逃す。葉のかぶりの分類器も多数派基準を超えていない。実用精度や熟練者の栽培判断を再現した結果とは主張できず、現時点では作業指示へ接続しない。

### 10月2日に修正・点検した点

- 輝度基準の画像内中央値が、正解ラベルによって不明・未入力の実を除外していた。実運用でラベルは使えないため、全ての実を含めるよう修正した。合計の一致数は旧101件から97件、初回だけでは旧37件から35件に訂正した。
- 実の縁だけの受光、逆光、枠中央に重なる明るい葉を確認した。中央輝度だけでは状態を十分に表せない。
- 前回の事前学習モデルの中央切り抜きは、143枠中17枠で枠領域の一部を入力から外していた。縦横比を保ち、枠全体と周囲を残す224×224入力を用意した。上表のMobileNetは**旧入力の結果**で、新入力の精度は未評価。
- ラベルを変更せず、全143枠の周囲・枠全体・旧入力・新入力案を並べたオフライン確認一覧を作成した。前処理の2件の回帰確認は通過した。

## 本選の案内方針と接続条件

中央の1個だけを選ぶ方式から、画面内の判定可能な複数の実を対象にする方針へ更新している。位置を説明しながら対象ごとに案内する。将来の作業判定が成立した場合、初期の読み上げ順は`take`→`keep`、中断・再撮影は「次」。同じ位置説明で複数の実を区別できない場合は、切断指示を保留する。葉の個体位置の案内は現在の必須範囲から外した。

現行の[判定スキーマ](../../backend/app/schemas/detections.py)は、`trigger_type=center`を主案とし、1件ごとに対象と判定を持つ。`trigger_type`は既存契約では対象指定方法の区分で、音声認識器の種類ではない。バッチ配列はあるが、同一撮影のフレームID、状態ラベル、発話順を表す契約は未更新。[セッション](../../backend/app/schemas/sessions.py)も単一作業と`plot_id`を前提にしている。複数対象の統合時には[API資料](../requirements/04-api.md)とFastAPI/OpenAPIを同時に更新する必要がある。

記録は入力識別子・モデル版・対象IDと枠・観察状態・判定と理由・処理時間・発話順を結び付ける。「指示した」と「実際に切った」は別のイベントにする。既存資料の信頼度0.5/0.8や重なり率0.6は例示値で、実証済みの閾値として採用しない。検出スコアを作業判断の信頼度として流用しない。

## 次の開発順

1. 明暗ラベルの解釈を確認し、既存の食い違い例で基準を合わせる。
2. 実全体を残す新入力で明暗・かぶりを再評価する。同じ評価結果に合わせた調整だけで成功を主張せず、別条件の検証データを確保する。
3. 自動保留の`unknown`を含め、陰・かぶりの見逃し、誤判定、保留率を別々に測る。熟練者と許容上限を決める。
4. 採用可能な観察モデルをAndroidへ組み込み、全対象の処理時間を測る。栽培判断へ進む場合は別途、適用条件と熟練者承認ラベルが必要。
5. Piとの画像取得、位置付き音声、中断・再撮影、記録APIを接続し、最初の音声までの遅延と対象の特定成功率を実機で測る。

本選で示す範囲は、果実検出の実機動作、観察状態の試作、栽培上の作業判断を区別して説明する。未検証の摘果・摘葉判断を完成済みと扱わない。
