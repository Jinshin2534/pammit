# 機能要件・非機能要件

## システム構成

```
■ 帽子（Raspberry Pi Zero 2 W）── I/O のみ
    カメラV3   → MJPEG で常時配信
    マイク     → PCM 送信
    スピーカー ← PCM 受信・再生
         ↕ Wi-Fi（スマートフォンのテザリング経由）
■ スマートフォン（Android / React Native）── 頭脳
    YOLO推論（TFLite）/ 判定計算 / 一次応答 / Realtime API 仲介 / アプリ画面
         ↕ LTE
■ AWS（EC2 + RDS）
    記録 / 週次スケジュール生成 / RAG
```


## ユースケース

### UC-1 アルバイトが摘果する ★主軸

```
1. アプリで「3番ハウス・摘果」の作業セッションを開始する
2. 判定したい実を視野の中央に入れる（カメラは帽子にあるので、頭を向けた方向が対象になる）
3. トリガーで、その瞬間のフレームをスマートフォンが推論
4. 判定 → 帽子のスピーカーが「摘んでいいです」（0.3秒・定型音声）
5. 迷えば「なんで?」と聞く → Realtime API が理由を説明（2〜3秒）
6. 判定結果がセッションに紐づいて蓄積される
```

**スマートフォンはポケットの中にあり、画面は見ない。** 音声だけで作業が回る。

### ~~UC-2 収穫でサイズを判定する~~（廃止）

規格板を不要にする機能だったが、**廃止した。**

スケール基準となる手袋マーカーを採用しないため、絶対サイズ（mm）が測れない。
かつ現地調査により、**収穫のサイズ判断は2日で慣れる**ことが判明している。

**摘果・摘葉に集中する。**

### UC-3 作業ログを記録する

### UC-5 農家さんが進捗と習熟度を確認する

園地ごとの進捗と、作業者ごとのAI一致率を見る。
**「誰にどこを教えるべきか」が分かり、付きっきりの負担が減る。**

| ID | 機能 | 優先度 | 内容 |
|---|---|---|---|
| F-01 | 作業セッション管理 | **必須** | アプリで明示的に開始・終了。園地と作業種別を指定 |
| F-02 | 判定結果の受信・蓄積 | **必須** | トリガーごとの判定を保存する（相対サイズ・密集度） |
| F-03 | 作業ログ記録 | **必須** | 帽子作業は自動、その他は選択式UI（3タップ） |
| F-04 | **週次スケジュール提案** | **必須** | 栽培暦・進捗・気象からルールで日程を組み、文章化のみLLM |
| F-05 | 判定精度の集計 | **必須** | 評価用データセットに対するAI一致率 |
| F-06 | AI相談・判定の理由説明 | 高 | Realtime API + Function Calling |
| F-07 | 年間カレンダー閲覧 | **保留** | 旬単位。**実際に使われているかヒアリング後に判断** |
| F-08 | ~~判定フィードバック~~ | **不採用** | 本選までに運用データが溜まらないため |
| F-09 | 管理者画面 | 中 | 進捗・AI一致率。**最小限に留める** |
| F-10 | センサーデータ受信 | 中 | BME280・土壌水分。常設ユニットから |
| F-11 | 気象データ取り込み | 中 | 露地のみ使用 |
| F-12 | 学習データのエクスポート | 低 | Roboflow連携 |

### 実装しない機能

以下は**裏取りができるまで実装しない**。
データは記録しておき、確認が取れ次第あとから追加できる状態にする。

- PHI警告・農薬使用回数チェック
- 灌水タイミングの提案
- 熱中症警告
- 判定フィードバック（F-08）

さらに、以下も扱わない。

| 扱わないもの | 理由 |
|---|---|
| **見逃しの検出**（AIが視界を探索して「まだあります」と教える） | 探索は判定より再現率の要求が高い。間違った場所を指すと信頼を失う |
| **剪定支援** | 柑橘の剪定は2〜3月。10月までにデータが撮れない。**今後の展望として提示する** |
| 「丁寧に扱う」促し | **保留。** 実装コストは低いが、採否は撮影結果を見てから判断する |

### F-04 の実装方針

| 処理 | 実装 |
|---|---|
| タスクを出す | 栽培暦テンプレート（ルール） |
| 進捗を出す | 作業ログとセッションから算出 |
| 天候による調整 | 気象予報（ルール） |
| 順序を決める | 期限と優先度（ルール） |
| **文章にする** | **LLM** |

生成は園地ごと、表示はロール別に分ける。

- 農家さん（owner）… 経営判断（「午前中に灌水を」）
- 作業者（worker）… 作業指示（「今日は3番ハウスの摘果です」）

トップには「今日行く予定の園地」の1本だけを出し、残りは一覧から辿る。

**前提**: 栽培暦テンプレートのデータ化が必須。JAの紙の栽培暦を手で打ち込む（2〜3時間）。

### F-05 の測定方法

**評価用データセットに対するAI一致率のみをKPIの根拠とする。**
運用中の修正は F-08 を不採用としたため存在しない。

- 学習用と評価用を分ける（学習に使ったデータで測っても意味がないため）
- 正解ラベルはベテラン農家の判定とする
- **サンプル数を必ず併記する**。「95%」より「サンプル420件で92.4%」のほうが信頼される

評価用データセットの作成方法はAI担当に委ねる。

## 非機能要件

| ID | 項目 | 要件 |
|---|---|---|
| N-01 | 応答時間 | **一次応答**はトリガーから **1秒以内**。二次応答は3秒まで許容 |
| N-02 | 可用性 | デモ時に停止しないこと。単一障害点は許容する |
| N-03 | 通信 | 畑でWi-Fi利用可。瞬断時はローカル保持し復帰後に再送（**冪等キー必須**） |
| N-04 | 端末負荷 | 画面OFF時はトリガー推論のみ。**常時推論はしない** |
| N-05 | データ保全 | 作業ログを欠損させない |
| N-06 | 拡張性 | 農園単位でデータを分離できる設計にする |
| N-07 | 会場ネットワーク | **本選会場にネット環境はない。** 一次応答はオフラインで完結すること |

### N-01 の根拠

作業のリズムを崩すと、音声ガイドそのものが邪魔になる。
判断を待つ時間が、迷って自分で決める時間より長ければ使われない。

### N-07 の含意

一次応答（判定と定型音声）が完全にオフラインで動くため、通信が死んでも中核機能は止まらない。
二次応答だけが「今は詳しい説明ができません」になる。**デモが全滅しない設計になっている。**

本選前に通信断のリハーサルを行うこと。

## 音声応答の二段構え

| | 一次応答 | 二次応答 |
|---|---|---|
| きっかけ | 判定トリガー | 「なんで?」と聞く |
| 実装 | 定型音声 | OpenAI Realtime API |
| 遅延 | 0.3秒 | 2〜3秒 |
| 通信 | 不要 | 必要 |

二次応答は Function Calling で振り分ける。

```
judge_current_frame()    → 目の前の実の判定根拠
search_knowledge(query)  → ベテラン知識のRAG検索
get_work_history(plot)   → 過去の作業ログ照会
```

## 信頼度に応じた振る舞い

エッジ推論の精度が未知であるため、信頼度で応答を分ける。閾値はDBに持ち、実力が判明してから調整する。

| confidence | verdict | 音声 |
|---|---|---|
| 0.8以上 | `take` / `keep` | 「摘んでいいです」 |
| 0.5〜0.8 | `take` / `keep` | 「たぶん摘んでいいですが、自信がありません」 |
| 0.5未満 | `unknown` | 「判断できません。農家さんに聞いてください」 |

**初心者向けの道具が自信満々に間違えるのが最も避けたい状態である。**
「わかりません」と言える設計により、精度が低くても製品として成立する。

## 認証

農家さんが作業者を事前登録し、**4桁PIN**でログインする。

アルバイトにアカウント登録とパスワード管理をさせるのは現実的でない。
（手袋マーカーによる自動識別の案は廃止した）

| 手段 | 用途 |
|---|---|
